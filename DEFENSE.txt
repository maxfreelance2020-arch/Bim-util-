ПАМЯТКА ДЛЯ ЗАЩИТЫ: КАК ОБЪЯСНИТЬ СВОЙ КОД
===========================================

Как читать решение:
1. Сначала найдите main: там выбирается способ запуска и открываются файлы.
2. Посмотрите основную функцию своей задачи: print_info, copy_remaining
   или process_image.
3. Разберите read_number, если она есть в вашей задаче.
4. Найдите формулу, которая выполняет именно ваше преобразование.
5. Проверьте себя по вопросам в конце памятки.

Чтобы объяснить строку преподавателю, скажите:
какие данные берёт эта строка, что с ними делает и зачем это программе.


1. ЧТО ТАКОЕ BMP В ЭТИХ ЗАДАЧАХ
-------------------------------

Картинка состоит из пикселей. У каждого пикселя есть три цветовых канала:
R — красный, G — зелёный, B — синий.
Каждый канал — целое число от 0 до 255.
(0, 0, 0) — чёрный, (255, 255, 255) — белый.

Вход гарантированно 24-битный: на пиксель приходится 24 бита = 3 байта.
Один байт хранит один канал. В BMP каналы записаны в порядке B, G, R.

Например, цвет RGB (200, 100, 50) в файле лежит тремя байтами:
    50 100 200

Перед пикселями находятся заголовки: служебная информация о картинке.
Число 54 в коде — это первые 14 + 40 байтов:
14 байтов заголовка файла и 40 байтов основного описания картинки.
Это не означает, что пиксели у любого BMP начинаются с позиции 54.
Их настоящая позиция записана в поле bfOffBits.

Позиции нужных полей, считая первый байт BMP позицией 0:
    0..1    подпись BM;
    10..13  bfOffBits — где начинаются пиксели;
    14..17  размер заголовка описания картинки;
    18..21  ширина;
    22..25  высота со знаком;
    26..27  число плоскостей, должно быть 1;
    28..29  число бит на пиксель, здесь 24;
    30..33  вид сжатия, здесь 0 — BI_RGB.

Все эти позиции относятся к BMP. В input.bin перед BMP дополнительно
расположена строка команды, поэтому сначала читаем её через fgets.


2. ЗАЧЕМ НУЖНА read_number
--------------------------

В BMP четырёхбайтовые числа хранятся младшим байтом вперёд.
Это порядок little-endian.

Если четыре байта равны b0, b1, b2, b3, число равно:
    b0 + b1*256 + b2*65536 + b3*16777216.

Почему 256? Один байт имеет 256 возможных значений.
Вес следующего байта в 256 раз больше веса предыдущего:
    1, 256, 256*256, 256*256*256.

Например, ширина 305 хранится как байты:
    49 1 0 0
Получается 49 + 1*256 = 305.

Параметр bytes[] — массив байтов, из которого читаем.
Параметр start — индекс первого из четырёх нужных байтов.
const означает, что функция не меняет содержимое этого массива.

Функция возвращает long long, потому что четыре байта могут задавать
число до 4294967295, а в обычный 32-битный int положительным оно не помещается.
Суффикс LL у констант заставляет выполнять умножение в типе long long
с самого начала, до возможного переполнения int.

read_number(header, 18) читает ширину, а read_number(header, 10) —
смещение пикселей. Различается только начальная позиция.

Мы не читаем весь BMP в структуру C: его поля могут отличаться от расположения
полей структуры в памяти. Массив байтов даёт явно заданные позиции.


3. ПОЧЕМУ ВЫСОТА ИНОГДА ОТРИЦАТЕЛЬНАЯ
-------------------------------------

Знак поля высоты сообщает порядок строк в файле:
    положительная высота — сначала нижняя строка;
    отрицательная высота — сначала верхняя строка.

Настоящая высота картинки — абсолютное значение этого поля.

read_number собирает четыре байта как неотрицательное число.
Для отрицательной высоты -h получается число 2^32 - h.
Поэтому h = 4294967296 - прочитанное значение.
Проверка значения от 2147483648 определяет, что в 32-битном поле установлен
бит знака. Это не обычная положительная высота.

Пример: -183 прочитается как 4294967113.
4294967296 - 4294967113 = 183.

Мы берём положительную высоту для числа повторений цикла и для вывода info.
В цветовом преобразовании сам заголовок не изменяем и строки не переставляем.
Каждый пиксель обрабатывается независимо, поэтому расположение строк
остаётся правильным при обоих вариантах знака.


4. СТРОКИ ПИКСЕЛЕЙ И ВЫРАВНИВАНИЕ
---------------------------------

В файле каждая строка занимает количество байтов, кратное 4.
Цвета занимают width * 3 байтов. После них бывает 0, 1, 2 или 3 лишних байта.
Они называются байтами выравнивания и цветами пикселей не являются.

Формула в коде:
    row_size = (width * 3 + 3) / 4 * 4;

Здесь деление целочисленное: дробная часть отбрасывается.
Прибавление 3 перед делением позволяет округлить вверх, а не вниз.

Ширина    Байты цветов    Вся строка    Выравнивание
1         3               4            1
2         6               8            2
3         9               12           3
4         12              12           0

Например, для ширины 3:
    (3*3 + 3) / 4 * 4 = 12 / 4 * 4 = 12.

Массив row[6000] хранит одну строку вместе с выравниванием.
При ширине до 2000 даже с выравниванием понадобится не больше 6000 байтов.

Внутренний цикл выполняется width раз. Поэтому он меняет только пиксели,
а байты выравнивания остаются прежними.
Вся строка, включая выравнивание, записывается одним fwrite.

position = x * 3 — индекс первого байта пикселя с номером x.
row[position] — B, row[position + 1] — G, row[position + 2] — R.
Первый пиксель имеет x = 0 и начинается с индекса 0.


5. ЧТО ПРОИСХОДИТ В КАЖДОЙ ЗАДАЧЕ
---------------------------------

I1A. Информация о картинке
    main открывает вход и место для результата.
    print_info читает первые 54 байта, достаёт ширину и высоту.
    Высоту приводит к положительной.
    fprintf(output, "%d %d", width, height) записывает два целых через пробел.
    В режиме CATS это output.txt, с аргументами — терминал.
    Сами пиксели для этой задачи читать не требуется.

I1B. Пересохранение
    main читает только строку команды, если это режим CATS.
    Затем copy_remaining копирует всё оставшееся.
    После строки команды находится ровно исходный BMP.
    Пересобирать заголовки и отдельно разбирать цвета не требуется.
    Сохраняются заголовки, пиксели, выравнивание и любые дополнительные байты.
    На последнем чтении count может быть меньше 4096:
    записать нужно именно count байтов, а не всегда весь массив.

I2A. Негатив
    Для каждого пикселя меняем три канала:
        new_B = 255 - B;
        new_G = 255 - G;
        new_R = 255 - R.
    Цвет RGB (200, 100, 50) превращается в (55, 155, 205).
    Чёрный превращается в белый.
    Два последовательных негатива восстанавливают исходный цвет:
        255 - (255 - value) = value.

I2B. Оттенки серого
    Яркость по условию:
        Y = 0.299*R + 0.587*G + 0.114*B.
    Глаз по-разному воспринимает каналы: у зелёного вес больше.
    Поэтому обычное среднее (R + G + B) / 3 не подходит под требование.

    Используем ту же формулу в целых числах:
        gray = (299*R + 587*G + 114*B + 500) / 1000.
    +500 даёт округление к ближайшему целому.
    Коэффициенты суммируются в 1000, результат находится между 0 и 255.
    Самая большая сумма до округления — 255000: она помещается в int.
    Присваиваем одно значение всем трём каналам: R = G = B = gray.

    Для красного (255, 0, 0):
        (299*255 + 500) / 1000 = 76745 / 1000 = 76.
    Отклонение от исходной яркости 76.245 меньше единицы.

I2C. Яркость
    change — значение N из команды bright N.
    Для каждого канала вычисляем value = исходный канал + change.
    Если value < 0, берём 0. Если value > 255, берём 255.

    Временная переменная value имеет тип int.
    Сначала ограничиваем диапазон, затем сохраняем в unsigned char.
    Если сразу сохранить результат в байт, 250 + 10 может превратиться в 4,
    а нам нужно 255. Это переполнение диапазона байта.

    bright 10: (250, 128, 3) -> (255, 138, 13).
    bright -10: (250, 128, 3) -> (240, 118, 0).
    bright 0 ничего не меняет.

I2D. Чёрно-белый документ
    threshold — значение T из команды threshold T.
    Считаем brightness = 299*R + 587*G + 114*B.
    Это исходная яркость, умноженная на 1000, без округления.

    Сравниваем brightness >= threshold * 1000:
        условие выполнено — color = 255;
        иначе — color = 0.
    Всем трём каналам записываем color.
    Равенство порогу даёт белый пиксель, как требуется в условии.

    При T = 128 красный (255, 0, 0) становится чёрным:
        76245 < 128000.
    Жёлтый (255, 255, 0) становится белым:
        225930 >= 128000.

    При T = 0 любой пиксель белый, включая исходный чёрный.
    При T = 255 белым по точной формуле останется только исходный белый.
    Допуск около порога в проверяющей системе позволяет некоторые близкие
    цвета, но наше решение применяет саму формулу без такого послабления.


I2E. Сепия
    Каждый новый канал — своя сумма исходных R, G и B:
        R' = 0.393*R + 0.769*G + 0.189*B;
        G' = 0.349*R + 0.686*G + 0.168*B;
        B' = 0.272*R + 0.534*G + 0.131*B.

    В коде коэффициенты умножены на 1000:
        new_red = (393*red + 769*green + 189*blue + 500) / 1000;
    Для зелёного и синего расчёт такой же, со своими коэффициентами.
    Все слагаемые неотрицательные. +500 перед целочисленным делением
    округляет к ближайшему целому, а дробную часть 0.5 — вверх.

    Например, для R=0, G=2, B=58 новое значение красного:
        (769*2 + 189*58) / 1000 = 12.5, после округления получается 13.

    Сначала сохраняем исходные каналы в red, green, blue и вычисляем
    три новых значения в переменных int. Затем ограничиваем каждый
    результат сверху числом 255 и записываем в массив в порядке B, G, R.
    Для неотрицательных значений округление с последующим ограничением
    даёт тот же результат, что ограничение до 255 перед округлением.

    Если записать новый красный раньше и использовать его в формуле
    зелёного, цвет будет неверным: формулы требуют исходные значения.
    int также нужен, чтобы сумма не переполнила однобайтовый канал.
    Наибольшая сумма до округления: (393+769+189)*255 = 344505.
    Она помещается в int, но не помещается в unsigned char.

    Белый (255, 255, 255) превращается в (255, 255, 239):
    первые два канала ограничиваются до 255, третий равен 238.935
    до округления. Чёрный остаётся чёрным.
    Цвет (200, 100, 50) превращается в (165, 147, 114).


6. КАК РАБОТАЕТ main
--------------------

argc — количество аргументов, включая имя программы.
argv — массив строк. argv[0] — имя/путь запущенной программы.

Без аргументов argc равен 1. Это режим CATS.
main открывает input.bin в режиме rb и читает первую строку через fgets.
fgets читает LF вместе со строкой, поэтому в файле следующим остаётся BMP.
В bright/threshold из строки ещё извлекается числовой параметр.

Пример обычного запуска:
    imgtool bright 10 in.bmp out.bmp
    argc = 5
    argv[0] = "imgtool"
    argv[1] = "bright"
    argv[2] = "10"
    argv[3] = "in.bmp"
    argv[4] = "out.bmp"

Индексы argv зависят от команды: у bright и threshold на один параметр больше.
Перед обращением к argv проверяется нужное argc.
Оператор || вычисляется слева направо и останавливается, если условие истинно.
Поэтому при неверном argc выражение со strcmp(argv[1], ...) не выполняется.

strcmp(a, b) возвращает 0 при совпадении строк.
Указатели на строки нельзя корректно сравнивать оператором == для проверки
совпадения их текста, поэтому используется strcmp.

sscanf читает значения из строки, а не из файла.
"%31s %d" означает: прочитать слово не длиннее 31 символа и целое число.
В command_name[32] остаётся ещё один элемент для завершающего нулевого байта.
&change или &threshold — адрес переменной, куда sscanf должен записать число.
sscanf возвращает число успешно заполненных переменных; здесь нужно 2.

В обычном запуске параметр уже является отдельной строкой argv[2],
поэтому применяется sscanf(argv[2], "%d", &change) либо аналог для threshold.
Дополнительно проверяются допустимые границы параметра.

Результаты вычисляются одними и теми же функциями в обоих режимах.
Отличаются источник данных и место, куда записывается результат.


7. ФАЙЛЫ, ТИПЫ И ОПЕРАТОРЫ C
----------------------------

#include <stdio.h>
    Подключает объявления стандартных функций работы с файлами и выводом.

#include <string.h>
    Подключает strcmp для сравнения строк.

FILE *input
    Указатель на объект открытого файла, с которым работает библиотека C.
    Мы не реализуем указатели и файловую систему вручную.
    input — источник данных, output — место записи.

fopen("input.bin", "rb")
    Открывает файл на чтение в двоичном режиме.
    Возвращает указатель FILE* при успехе или NULL при ошибке.

"wb"
    Открывает файл на запись в двоичном режиме.
    Создаёт файл или очищает существующий файл с таким именем.

"w"
    Текстовая запись. Подходит для output.txt с числами.

Почему BMP читаем через rb и пишем через wb
    В двоичном режиме байты не интерпретируются как переводы строк.
    Это особенно важно в Windows: файл содержит любые значения байтов,
    включая 10, 13 и 26, и их надо сохранить.

unsigned char
    Здесь хранит один байт от 0 до 255.
    Обычный char может быть знаковым и представлять значения 128..255
    отрицательными числами, что мешает вычислениям цветов.

unsigned char header[54]
    Массив из 54 байтов для начальных полей BMP.
    Индексы идут от 0 до 53.

unsigned char row[6000]
    Массив для текущей строки пикселей и её выравнивания.

unsigned char buffer[4096]
    Массив для копирования порции файла.
    Число 4096 — удобный размер буфера, оно не является свойством BMP.

size_t
    Стандартный тип для размеров объектов и числа элементов.
    fread и fwrite возвращают size_t. Поэтому count имеет такой тип.

sizeof(header), sizeof(row), sizeof(buffer)
    Размер соответствующего массива в байтах в месте его объявления.
    Для этих массивов один элемент занимает один байт.

fread(header, 1, sizeof(header), input)
    Пытается прочитать sizeof(header) элементов размером 1 байт из input.
    Возвращает, сколько элементов действительно прочитано.
    Если их меньше ожидаемого, заголовок прочитан не полностью.

fwrite(row, 1, (size_t)row_size, output)
    Записывает row_size байтов из row.
    Результат сравнивается с запрошенным числом байтов для проверки ошибки.

(size_t)row_size, (int)width_value, (unsigned char)value
    Явное преобразование типа. Перед сужением диапазон проверен
    или гарантирован формулой.
    Скобки указывают, к какому типу преобразовать значение.

fgetc(input)
    Читает один байт и возвращает его как int.
    int нужен, чтобы отличить все 256 значений байта от специального EOF.

EOF
    Специальный результат функции чтения: байт получить не удалось.
    Это может означать конец файла или ошибку чтения.
    Если байт был обязателен, любой EOF считается ошибкой.
    При обычном копировании конец файла ожидаем; ошибку отличает ferror.

fputc(byte, output)
    Записывает один байт. Возвращает EOF, если запись не удалась.

ferror(input)
    Проверяет, произошла ли ошибка работы с потоком.
    В copy_remaining помогает отличить нормальный конец от ошибки чтения.

fclose(input)
    Закрывает файл. При записи также завершает сохранение буферизованных данных.
    Ошибка записи иногда выявляется только при закрытии, поэтому результат
    fclose(output) тоже проверяется.

stdout
    Стандартный вывод программы. При обычном запуске info это терминал.
    stdout — тоже файловый поток, с ним работает fprintf.
    В конце программы его можно закрыть через fclose, как в нашем коде.

fprintf(output, "%d %d", width, height)
    Печатает два int в выбранный поток.
    %d — место для одного целого числа, между ними обычный пробел.
    Отрицательный результат fprintf означает ошибку записи.

return 0 / return 1
    В наших функциях: 0 — успех, 1 — ошибка.
    В main это код завершения всей программы.
    В read_number возвращаемое значение имеет другой смысл: прочитанное число.

=
    Присваивание. Записывает вычисленное справа значение в переменную слева.

== / !=
    Сравнение на равенство / неравенство.

< / > / >=
    Меньше / больше / больше либо равно.

||
    Логическое «или». Истинно, если истинно хотя бы одно условие.

int result = process_image(input, output)
    Вызывает функцию обработки и сохраняет её код завершения.
    Позже ошибки закрытия файлов также могут сделать result равным 1.

for (int y = 0; y < height; y++)
    Начинает с y = 0; повторяет, пока y меньше height;
    после каждой итерации увеличивает y на единицу.
    Всего обрабатывает height строк.

while ((count = fread(...)) > 0)
    Сначала сохраняет число прочитанных байтов в count,
    затем проверяет, что оно больше нуля.
    Внешние скобки позволяют сравнить именно результат присваивания.
    Цикл заканчивается, когда прочитать новые байты не удалось.

Фигурные скобки { }
    Объединяют команды в тело функции, цикла или условного оператора.

Точка с запятой ;
    Завершает инструкцию языка C.

Комментарии /* ... */
    Поясняют код человеку и не выполняются программой.


8. ЧТО СОХРАНЯЕТСЯ В ЦВЕТОВЫХ КОМАНДАХ
--------------------------------------

1. Первые 54 байта заголовка.
2. Все байты между ними и pixel_offset.
3. Все строки пикселей; внутри них меняются только цветовые каналы.
4. Байты выравнивания каждой строки остаются исходными.
5. Все данные после последней строки.

Размер картинки и способ хранения строк не меняются.
Поэтому поля размеров в заголовке уже правильные и пересчитывать их не нужно.
Если входной biSizeImage равен 0, это допустимо для BI_RGB; так и оставляем.

Сжатые BMP, 32-битные BMP и картинки за пределами 1..2000
не входят в формат входа этих заданий. Проверки формата в process_image
защищают рабочие массивы и помогают завершить программу с ошибкой,
если случайно передан неподходящий файл.


9. СКОРОСТЬ И ПАМЯТЬ
---------------------

info читает только небольшой заголовок: объём работы не зависит от числа пикселей.
copy выполняет работу, пропорциональную числу байтов файла.
Цветовые команды обходят все пиксели один раз и копируют остальные байты файла.

Одновременно в памяти находится одна строка, а не вся картинка.
Основные массивы: 6000 байтов для строки, 54 для заголовка
и 4096 для копирования оставшихся данных.
Это несколько килобайт плюс служебная память библиотеки и программы.

Максимальная картинка содержит 2000*2000 = 4 000 000 пикселей,
или 12 000 000 байтов цветов. Код не создаёт в памяти массив такого размера.


10. ПРОВЕРЬТЕ СЕБЯ ПЕРЕД ЗАЩИТОЙ
--------------------------------

Вопрос: Где начинается выполнение?
Ответ: С main. Остальные функции выполняются, когда main или другая функция
их вызывает.

Вопрос: Почему сначала fgets, а потом fread?
Ответ: Первая строка input.bin — текстовая команда, после LF начинается BMP.
fgets забирает именно эту строку. fread затем читает двоичные данные.

Вопрос: Почему не читать команду через scanf с пробелом в конце формата?
Ответ: Такой пробел может поглотить байты BMP, которые считаются пробельными.
Мы явно заканчиваем чтение команды на переводе строки через fgets.

Вопрос: Почему нельзя инвертировать каждый байт файла?
Ответ: Кроме цветов там есть заголовки, дополнительные данные и выравнивание.
Их изменение испортит формат либо изменит лишние данные.

Вопрос: Почему зелёный канал находится по индексу position + 1?
Ответ: У пикселя три байта B, G, R. Первый индекс — position.

Вопрос: Нужно ли переворачивать строки при отрицательной высоте?
Ответ: Для этих семи команд — нет. Размеры и порядок строк сохраняются,
а цвет каждого пикселя меняется независимо от соседей.

Вопрос: Почему read_number использует long long, хотя размеры до 2000?
Ответ: Функция сначала читает сырое четырёхбайтовое значение, в том числе
отрицательную высоту в её двоичном представлении. Оно может быть около 2^32.

Вопрос: Для чего переменные width_value и height_value, а затем width и height?
Ответ: Сначала безопасно читаем и проверяем большие сырые значения,
затем преобразуем проверенные размеры в удобный тип int.

Вопрос: Что будет при неполном чтении строки пикселей?
Ответ: fread вернёт меньше row_size, process_image вернёт 1,
main закроет файлы и завершит программу с кодом ошибки.

Вопрос: Где находится главное действие моей команды?
Ответ: У info — чтение размеров и fprintf, у copy — цикл fread/fwrite,
у цветовых команд — внутренний цикл по x с соответствующей формулой.

Вопрос: Что означают PE и WA в правилах проекта?
Ответ: PE означает нарушение выходного формата.
WA означает, что изображение или размеры не соответствуют условию.
